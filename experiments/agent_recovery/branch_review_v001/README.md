## 目的与范围

用户将 recovery 改为两次调用：第一次同时识别回退节点有哪些可选支路、此前实际走了哪条；第二次输出局部 R2R recovery 指令。本版只实现第一次调用。最初按用户要求仅编写，随后用户明确指定 v006 十例、GPU3 Qwen27B，授权执行并导出可视化。

核心定义：**支路是当前同一决策位置可以直接作出的选择，不能是先选择某条通路之后才出现的下一层选择。** 必要的短距离靠近入口仍可属于当前选择，不把“直接选择”误解为只能原地转弯。

此前的支路盘点和已走路线识别为两个调用，见 [历史单目协议](../../agent_route_choice/human_v002/run_20261107_01/README.md)。本版合并这两个视觉任务；替代支路选择与 R2R 指令生成属于后续第二次调用，尚未在本版定义或接入。

C 指去重后保留的回退节点对应的实际观测 step，不是节点确认时刻。所有图片来自同一 episode。

| 3 | C_right70 | C | 同一节点位置，原生相机朝向向右 70° |
| 4 | C_plus2 | C+2 | 该 step 实际取得的原生前视图 |
| 5 | C_plus5 | C+5 | 该 step 实际取得的原生前视图 |
| 6 | C_plus8 | C+8 | 该 step 实际取得的原生前视图 |
| 7 | C_plus10 | C+10 | 该 step 实际取得的原生前视图 |

用户描述为后续 15 step 范围内采样，具体采用其明确列出的 +2、+5、+8、+10，共四张；不另加 C+15。后续图像间隔不等，使用各自当时真实朝向，不能宣称它们都对齐 C 的 0°。支路输出方向统一相对于 C_front。

前三张属于同一节点位姿的三向观测，不代表三个导航动作。现有 ±70° 资源是按历史相机位姿重新渲染的三图，来源见 [补采记录](../../multiview_capture/v006_pose70/run_20261121_01/README.md)；该组 0° 图也属于补采图。后四张使用真实历史原生前视图，不用辅助全景图替代。

这里的“后续”相对于 C；真正发送请求时七张图都须已获得。若某例缺图，标为输入不完整，不复制、补造或静默改成其他偏移。十例实际运行使用现有完整的 70 张原始 PNG，具体节点、帧号和哈希见运行记录；这是离线识别，未声称在上游首次报警时所有后续图就已可用。

## 模型请求与输出

[中文 Prompt](prompt_zh.txt) 为实际 system 消息，[英文 Prompt](prompt_en.txt) 为逐项对照。user 消息按 [protocol.json](protocol.json) 的顺序附图像 ID、实际 step 与对应图片，并附 [output_schema.json](output_schema.json)。实际完整请求、原答与输入清单逐例保存。

模型输入为七图及其时间／视角标签。不提供原任务指令、参考路线、地图、世界坐标、候选正确答案、上游已选方向或上游错误理由。上游“该尝试需要纠正”只是本调用的触发背景，不是视觉上已证明某条支路错误的结论。

输出包含：

- `branches`：B1、B2……的当前支路清单；方向、入口外观、属于当前选择的依据和证据图像 ID。
- `previous_attempt`：实际走过的支路匹配；`identified` 时引用已有支路 ID，`uncertain` 时 `branch_id=null`，说明证据限制。
- `uncertainties`：其余无法确认的观察。自然语言均使用中文。

入口除 JSON Schema 字段约束外，还检查支路 ID 唯一且按 B1 起连续编号，以及已识别的 `branch_id` 存在于本次清单。格式合法不证明支路语义或路线识别正确。允许清单为空或只有一条，不强制构成路口。未知匹配不自动变成排除项。
